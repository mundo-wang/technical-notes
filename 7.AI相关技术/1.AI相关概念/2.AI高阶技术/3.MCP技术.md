回顾上一节描述的工具调用流程，平台在解析出大模型返回的工具名称与入参后，需要知道「去哪里调用、怎么调用」，也就是维护一份工具名称到调用地址、认证方式的配置映射，然后自行拼装`HTTP`请求发出去。这套做法的问题在于，每接入一个新工具，平台侧都要单独适配，编写对应的调用逻辑、处理各自的认证方式与数据格式，扩展成本很高。

`MCP`解决的正是这个问题。它定义了一套标准协议，规定工具服务端（`MCP Server`）必须以统一的格式暴露自己的能力，平台侧（`MCP Client`）只需实现一套通用的客户端逻辑，便能与任意符合协议的工具服务通信，无需再为每个工具单独适配。

在生活中类比一下就是，没有`MCP`之前，平台对接每个工具，就像给不同品牌的设备分别配一根专用充电线；有了`MCP`，相当于统一换成了`USB-C`接口，工具只要支持这个标准，平台插上就能用。

需要澄清一个常见误区：「平台将工具列表提供给大模型」、「大模型将工具调用意图返回给平台」以及「平台将工具执行结果返回给大模型」这三个环节的`JSON`结构，并不属于`MCP`的规范范畴。这份`JSON`结构属于大模型`API`层面的协议，由各模型厂商自行定义，不同厂商的格式存在差异，是模型接口层面的问题。`MCP`规范的仅是「平台如何与工具交互」这一环节。

`MCP`在通信格式上基于`JSON-RPC 2.0`，所有交互均遵循统一的请求与响应结构。`MCP`提供了包括初始化、工具、资源、提示词等在内的一系列标准能力，本文只聚焦与工具调用直接相关的主流程，即初始化握手、工具发现以及工具调用。

在本文关注的工具调用场景中，可以先将`MCP`理解为两个核心动作：通过`tools/list`发现`MCP Server`提供的工具，通过`tools/call`调用指定工具。前者解决「有哪些工具」的问题，后者解决「调用哪个工具以及传入什么参数」的问题。

正式交互开始前，`Client`与`Server`之间需要先完成一次握手，双方交换协议版本与各自支持的能力集，确认后续交互中哪些特性可以启用，再进入后续流程。握手完成后，平台调用`tools/list`接口询问「你有哪些工具」：

```json
POST /mcp HTTP/1.1
Host: mcp.example.com
Content-Type: application/json
Authorization: Bearer <token>

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {}
}
```

`MCP Server`会以统一格式返回工具列表：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "tools": [
      {
        "name": "get_weather",
        "description": "查询指定城市的实时天气信息",
        "inputSchema": {
          "type": "object",
          "properties": {
            "city": { "type": "string", "description": "城市名称" },
            "date": { "type": "string", "description": "查询日期，格式YYYY-MM-DD" }
          },
          "required": ["city", "date"]
        }
      },
      {
        "name": "search_web",
        "description": "通过关键词在互联网上检索实时信息，返回相关结果摘要列表",
        "inputSchema": {
          "type": "object",
          "properties": {
            "query": { "type": "string", "description": "搜索关键词" },
            "limit": { "type": "integer", "description": "返回结果数量，默认为5" }
          },
          "required": ["query"]
        }
      }
    ]
  }
}
```

平台获取工具列表后，`MCP Client`将其拼装成大模型`API`所要求的请求格式，发送给大模型，整个过程对`MCP Server`透明。

大模型返回工具调用意图后，平台解析出工具名称及入参，再通过`MCP`协议调用`tools/call`接口：

```json
POST /mcp HTTP/1.1
Host: mcp.example.com
Content-Type: application/json
Authorization: Bearer <token>

{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": {
      "city": "北京",
      "date": "2026-04-18"
    }
  }
}
```

`MCP Server`处理完成后，同样以统一格式返回执行结果：

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "{\"city\":\"北京\",\"condition\":\"晴\",\"temperature\":22}"
      }
    ],
    "isError": false
  }
}
```

`MCP Client`得到响应结果后，再将其拼装成对应大模型`API`的请求格式，发送给大模型，得到最终回答。

这里有必要说明鉴权的处理方式。`MCP`协议本身并未强制规定统一的鉴权方案，具体取决于`MCP Server`的部署形态。

若采用`stdio`模式，`Client`以子进程方式在本地启动`Server`，通信经由标准输入输出进行，安全边界由操作系统的进程权限保证，无需额外鉴权。这种模式常见于本地开发工具场景，例如`Claude Desktop`挂载本地`MCP Server`，在服务端`agent`场景中几乎不会采用。若将`Server`部署为远程服务，官方推荐基于`OAuth 2.1`的授权流程，`Client`在建立连接前完成授权并获取`Access Token`，后续每次发起`JSON-RPC`请求需在请求头中携带该`Token`。

上一节中，平台是自己维护配置、自己拼`HTTP`请求，每个工具的请求路径、认证方式、入参格式各不相同。引入`MCP`后，平台只需与`MCP Server`之间跑统一的`JSON-RPC`协议，工具内部怎么实现、去调哪个下游接口，平台完全不用关心。`MCP`把「工具名称到调用地址的配置映射」以及「拼装`HTTP`请求的适配逻辑」全部下沉到了`MCP Server`内部，平台侧只保留一套通用的调用逻辑。

除了`MCP`之外，`Agent`还可以直接通过`CLI`调用外部能力。`CLI`是另一种工具调用范式，允许`Agent`直接生成并在终端执行命令，例如`git`、`docker`、`kubectl`、`gh`、`aws`等。相比`MCP`，`CLI`最大的优势在于灵活性，已有的命令行工具无需额外封装即可接入，同时天然支持管道、重定向以及多命令组合。

但灵活性也意味着更大的安全风险。如果直接为`Agent`提供类似`run_command(command)`的能力，那么权限边界就会从某个明确的结构化工具，扩大为「执行当前环境允许执行的命令」，进而可能接触文件系统、网络、环境变量以及各类凭证。但是，`CLI`本身并不等于不安全，真正需要防范的是未经限制的`Shell`执行。生产环境通常需要结合`Sandbox`、命令白名单、目录与网络访问限制、凭证隔离、执行超时以及审计等机制，对`CLI`的执行权限进行约束。

因此，`MCP`和`CLI`并不是简单的替代关系。`MCP`更适合将能力以结构化、可发现、可治理的方式暴露给`Agent`，而`CLI`更适合复用已有的命令行工具。二者都可以调用本地或远程能力，市面上的`Agent`系统通常会采用混合方式，例如通过`CLI`复用`git`、`docker`、`kubectl`等已有工具，通过`MCP`连接数据库、内部业务系统以及第三方`SaaS`服务。
