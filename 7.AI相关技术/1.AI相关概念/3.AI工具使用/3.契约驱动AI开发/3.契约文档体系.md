这篇笔记明确契约驱动开发中契约的目录结构及各契约应包含的核心内容，为`AI`生成契约提供清晰的边界约束。

交付契约目录写在项目的根目录下，结构如下所示：

```scss
项目上下文.md          <-- 项目根目录，存放全局静态约定

交付契约/
├── <需求名称1>/
│   ├── v1/
│   │   ├── 1.产品契约.md
│   │   ├── 2.技术契约.md
│   │   └── 3.测试契约.md
│   └── v2/
│       ├── 1.产品契约.md
│       ├── 2.技术契约.md
│       └── 3.测试契约.md
│
└── <需求名称2>/
    └── v1/
        ├── 1.产品契约.md
        ├── 2.技术契约.md
        └── 3.测试契约.md
```

项目上下文文件与交付契约目录是否提交到远程仓库，应根据项目的协作模式与团队规范决定。

若项目采用单人开发模式，建议将二者一并提交到远程仓库，作为项目文档进行统一版本管理。若项目采用多人协作模式，则应根据团队是否已建立统一的契约驱动开发规范决定。若团队已明确将交付契约纳入协作流程，则应将二者一并提交到远程仓库，确保所有开发者遵循统一的文档体系开展需求开发。若团队尚未建立统一规范，则建议将二者加入`.gitignore`，仅在本地维护，以避免其他开发者看到相关文档后产生困惑，以及他人误修改相关契约文件内容。

无论采用哪种方式，都应确保开发者本人使用的`AI`能够正确读取并遵循交付契约中的约束信息。

项目上下文是后续所有契约编写与代码开发的基础，确保`AI`对项目具备统一、准确的认知。项目上下文以单文件形式存放在项目根目录下，仅包含项目中不易变更的静态约定，对于随代码迭代可能变化的信息（如具体模块清单、公共组件列表、接口定义、错误码等），文档中不展开详述，而是通过动态信息索引指明这些信息在代码库中的位置，由`AI`在需要时直接读取源码获取最新状态。

项目上下文的内容应根据项目实际情况灵活裁剪，避免过度文档化。建议包含以下章节：

| 章节 | 说明 |
|------|------|
| 项目基本信息 | 项目名称、背景、目标及核心业务领域 |
| 技术栈 | 开发语言、主框架、数据库、缓存、部署方式等核心技术选型 |
| 架构原则与分层约束 | 分层模式、层间调用规则、模块粗粒度边界原则 |
| 命名规范 | 包名、文件、变量、函数、结构体、接口、常量及数据库对象的命名规则 |
| 代码风格与基础约定 | 缩进、换行、注释、导包顺序、错误处理原则、结构体标签约定、日志要求 |
| 领域术语表 | 核心业务概念及专有名词解释，避免后续沟通歧义 |
| 关键全局约束 | 认证授权方式、统一响应/错误封装格式约定、敏感信息处理原则 |
| 动态信息索引 | 以表格形式指明错误码、公共组件、路由、模型等动态信息在代码库中的位置 |

上述章节为建议内容，可根据项目实际情况动态补充其他章节，但需与开发者沟通确认。

三类交付契约（产品契约、技术契约、测试契约）的编写应遵循以下原则：

1. 按需编写：根据需求等级（`L1`/`L2`/`L3`）及实际影响范围，灵活选择契约章节，避免过度文档化。
2. 最小必要集优先：每份契约优先确保核心章节完整，再根据实际需求补充扩展章节。
3. 聚焦本次版本：技术契约和测试契约仅关注当前版本（`vN`）的具体实现与验证，不涉及未来版本的规划内容。
4. 相互一致：三份契约中的业务描述、接口定义及测试用例必须保持一致，确保契约之间不存在矛盾或歧义。
5. 可执行、可验证：契约中的每项约束都必须明确、具体且可检查、可验证，避免模糊描述，确保能够直接指导开发与测试工作。

在确定具体契约的章节结构时，`AI`应遵循动态推断原则，避免机械套用固定列表。

首先，从需求描述、技术方案及代码现状中提取关键特征标签，识别需求涉及的核心业务与技术维度。在此基础上，确保契约类型的最小必要集得到完整覆盖，避免因章节精简而遗漏业务或技术本质。

对于可选扩展维度，应根据提取的特征标签进行正向筛选，同时反向排除明显无关的章节，避免过度文档化。随后执行缺口识别，逐一检查需求中的每个重要方面是否均有对应章节承载。若发现存在无法归入现有章节的重要内容，必须主动新增章节，并说明新增理由。最后进行精简校验，检查是否存在冗余章节，并对可以合并或删除的内容进行优化，确保契约厚度与需求复杂度相匹配。

上述推断原则适用于全部三类交付契约。最小必要集与可选扩展集仅作为章节设计的维度参考，而非封闭清单。`AI`应结合实际需求、技术方案及代码上下文进行综合推理，动态确定最终章节结构。

产品契约是前后端共同遵循的业务基准，用于明确本次需求的业务目标、业务规则、业务流程及范围边界。

产品契约的最小必要集覆盖以下核心维度：

| 章节     | 说明                                                         |
| -------- | ------------------------------------------------------------ |
| 需求背景 | 简述本次需求的业务背景、需要解决的问题及预期价值             |
| 业务目标 | 明确本次需求需要达成的具体、可衡量的业务目标                 |
| 业务规则 | 定义核心业务流程必须遵守的规则、约束条件及状态流转条件       |
| 业务流程 | 详细描述主业务流程，明确各环节的输入、处理逻辑及输出         |
| 需求范围 | 明确本次需求包含的功能点及不包含的内容，划定清晰的需求边界   |
| 边界条件 | 明确异常情况、极限值、空值处理及并发场景等业务约束           |
| 验收标准 | 定义需求完成的质量标准，为开发和测试提供明确、可执行的验收依据 |

产品契约的可选扩展集提供以下扩展维度参考：

| 章节             | 说明                                                         | 适用场景                                   |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------ |
| 用户角色与权限   | 明确涉及本次需求的用户角色及其操作权限                       | 涉及权限控制的需求                         |
| 原型图与交互说明 | 描述关键页面的布局、页面元素及交互行为，可引用原型图辅助说明 | 涉及前端页面改动的需求                     |
| 数据要求         | 明确核心业务数据的来源、格式、精度及有效期等要求             | 涉及数据展示或处理的需求                   |
| 性能要求         | 明确响应时间、并发量、吞吐量等性能指标                       | 高并发或性能敏感型需求                     |
| 兼容性要求       | 明确浏览器版本、移动端适配及接口版本兼容等要求               | 涉及多端兼容的需求                         |
| 后续展望         | 简要说明未来可能的迭代方向，仅提供必要的业务上下文，不展开具体规划 | `L3`需求拆分时，为后续阶段保留必要的上下文 |

需求等级与产品契约的裁剪规则如下：

| 需求等级 | 产品契约要求                                                 |
| -------- | ------------------------------------------------------------ |
| `L1`     | 可采用轻量级交付契约，重点描述业务目标、核心规则及范围边界，其余章节可根据实际情况大幅精简 |
| `L2`     | 需编写完整的产品契约，覆盖全部最小必要集，并根据实际需求选用可选扩展集 |
| `L3`     | 按阶段拆分需求，每个阶段独立编写产品契约。当前阶段聚焦本次交付范围，结尾可简要说明后续阶段的目标，为后续迭代保留必要上下文 |

技术契约用于明确本次需求的技术实现方案、架构约束、模块职责及具体实现要求。由于前后端在技术栈、架构设计及实现方式上存在差异，应分别编写前端技术契约和后端技术契约，确保技术要求清晰、职责边界明确。

后端技术契约的最小必要集覆盖以下核心维度：

| 章节           | 说明                                                         |
| -------------- | ------------------------------------------------------------ |
| 技术方案概述   | 描述本次需求的整体技术实现思路、涉及的后端模块及具体变更范围 |
| 模块职责与变更 | 明确各涉及模块的职责，以及新增、修改、删除的具体内容         |
| 接口设计       | 列出新增或变更的`API`，每个接口需包含路径、请求方法、请求参数、响应结构及错误码 |
| 数据结构设计   | 定义新增或变更的请求与响应结构体、内部模型及枚举类型         |
| 数据库变更     | 明确新增、修改、删除的数据库表、字段及索引，并提供对应的`SQL`变更脚本 |
| 核心业务逻辑   | 描述关键业务逻辑的实现步骤、算法及状态机流转过程             |
| 技术约束       | 明确必须遵守的架构规则（如禁止跨层调用、必须使用公共组件）、性能要求及安全约束 |

后端技术契约的可选扩展集提供以下扩展维度参考：

| 章节         | 说明                                                         | 适用场景                         |
| ------------ | ------------------------------------------------------------ | -------------------------------- |
| 依赖服务调用 | 明确外部服务及内部服务的调用接口、超时与重试策略、降级方案   | 涉及服务间调用的需求             |
| 缓存策略     | 设计缓存`Key`、过期策略及缓存一致性保障措施                  | 引入缓存的需求                   |
| 消息队列     | 明确消息`Topic/Queue`、生产者与消费者逻辑，以及消息消费幂等性保障措施 | 涉及异步消息的需求               |
| 事务与一致性 | 明确分布式事务方案、本地事务边界及事务回滚策略               | 涉及多表或多服务事务的需求       |
| 代码示例     | 提供关键业务逻辑的伪代码或代码片段，辅助理解技术实现方案     | 涉及复杂算法或特殊实现方式的需求 |
| 风险评估     | 识别技术实现中的潜在风险，并明确相应的应对措施               | 技术复杂度较高的需求             |

前端技术契约的最小必要集覆盖以下核心维度：

| 章节           | 说明                                                         |
| -------------- | ------------------------------------------------------------ |
| 技术方案概述   | 描述本次需求的整体前端实现思路、涉及的页面与组件及具体变更范围 |
| 页面与组件结构 | 列出新增或变更的页面及组件，明确各组件的职责与相互关系       |
| 路由与导航     | 明确新增或变更的路由、页面跳转逻辑及参数传递方式             |
| 交互逻辑       | 描述用户点击、输入、提交等操作对应的前端处理逻辑及状态变化   |
| 状态管理       | 明确涉及的全局状态、局部状态、状态流转及持久化策略           |
| 接口调用       | 列出本次需求涉及的后端接口，明确请求参数组装、响应数据处理及异常处理方式 |
| 表单与校验     | 明确表单字段、校验规则及错误提示方式                         |
| 技术约束       | 明确必须遵守的框架规范（如组合式`API`风格）、组件使用约束及样式规范 |

前端技术契约的可选扩展集提供以下扩展维度参考：

| 章节           | 说明                                                         | 适用场景               |
| -------------- | ------------------------------------------------------------ | ---------------------- |
| 权限控制       | 明确页面级、按钮级的权限判断逻辑，以及无权限时的展示策略     | 涉及权限控制的前端需求 |
| 数据展示规则   | 规范列表排序、分页、空状态、加载状态及数据格式化规则         | 涉及复杂数据展示的需求 |
| 第三方组件与库 | 明确引入的外部组件或依赖库、使用方式及版本要求               | 需要引入新依赖的需求   |
| 响应式适配     | 描述不同屏幕尺寸下的页面布局、组件展示及交互差异             | 涉及多端适配的需求     |
| 代码示例       | 提供复杂交互或状态管理的伪代码及关键代码片段，辅助理解实现方案 | 涉及复杂实现逻辑的需求 |

需求等级与技术契约的裁剪规则如下：

| 需求等级 | 技术契约要求                                                 |
| -------- | ------------------------------------------------------------ |
| `L1`     | 可大幅精简，重点描述本次变更范围、接口或组件调整及核心业务逻辑，无需覆盖全部章节 |
| `L2`     | 需覆盖全部最小必要集，并根据实际需求选用可选扩展集           |
| `L3`     | 按阶段独立编写技术契约，当前阶段聚焦本次实际实现范围，不提前编写后续阶段的技术方案 |

测试契约用于明确本次需求的测试范围、测试策略、测试用例及预期结果，为自动化测试实施和质量验收提供依据。由于前后端在测试范围、测试重点及测试方式上存在差异，应分别编写前端测试契约和后端测试契约，确保测试要求明确、验证标准统一。

后端测试契约的最小必要集覆盖以下核心维度：

| 章节         | 说明                                                         |
| ------------ | ------------------------------------------------------------ |
| 测试范围     | 明确本次需求需要测试的`API`接口清单、涉及模块及排除项        |
| 测试策略     | 明确接口测试类型、测试优先级及执行方式，统一通过`HTTP`请求调用后端接口，验证接口行为与响应结果 |
| 测试用例     | 每个测试用例包含用例编号、测试场景、前置条件、请求方法、请求路径、请求参数及预期结果 |
| 核心场景覆盖 | 覆盖正常业务流程、异常处理（参数非法、权限不足、资源不存在等）及边界条件 |
| 数据库验证   | 明确需要验证的数据库状态，如数据新增、修改、删除、事务回滚及幂等性，并说明验证方式 |
| 测试数据要求 | 明确测试所需的账号、权限、基础数据及测试数据的准备与清理方式 |

后端测试契约的可选扩展集提供以下扩展维度参考：

| 章节         | 说明                                              | 适用场景                         |
| ------------ | ------------------------------------------------- | -------------------------------- |
| 性能测试     | 明确性能测试指标、并发场景及预期响应时间          | 涉及性能敏感的需求               |
| 安全测试     | 明确越权访问、`SQL`注入、敏感信息泄露等安全验证点 | 涉及权限控制或敏感数据的需求     |
| 并发测试     | 描述并发请求场景、预期行为及数据一致性验证要求    | 涉及并发操作的需求               |
| 回归测试范围 | 明确需要回归验证的已有接口及业务功能点            | 涉及公共模块或公共接口变更的需求 |

前端测试契约的最小必要集覆盖以下核心维度：

| 章节             | 说明                                                         |
| ---------------- | ------------------------------------------------------------ |
| 测试范围         | 明确本次需求需要测试的页面、组件、交互流程及排除项           |
| 测试策略         | 明确测试执行方式，如浏览器自动化操作、`Playwright`脚本或人工操作 |
| 页面操作测试用例 | 每个测试用例包含用例编号、操作步骤（点击、输入、跳转等）、预期页面表现及数据展示结果 |
| 核心场景覆盖     | 覆盖正常操作流程、异常提示、边界输入、空状态及加载状态       |
| 数据验证         | 验证页面展示数据的正确性，以及用户操作引起的数据变化是否符合业务预期 |
| 测试环境要求     | 明确测试所需的账号、权限、后端接口状态及测试数据准备要求     |

前端测试契约的可选扩展集提供以下扩展维度参考：

| 章节         | 说明                                               | 适用场景               |
| ------------ | -------------------------------------------------- | ---------------------- |
| 兼容性测试   | 明确目标浏览器及设备清单，以及需要验证的兼容性要点 | 涉及多端兼容的需求     |
| 响应式测试   | 验证不同屏幕分辨率下的页面布局、组件展示及交互表现 | 涉及响应式布局的需求   |
| 权限测试     | 验证不同用户角色下的页面元素可见性及操作权限       | 涉及权限控制的需求     |
| 回归测试范围 | 明确需要回归验证的已有页面、组件及交互功能         | 涉及公共组件变更的需求 |

需求等级与测试契约的裁剪规则如下：

| 需求等级 | 测试契约要求                                                 |
| -------- | ------------------------------------------------------------ |
| `L1`     | 可精简为核心测试用例列表，明确主要验证点、测试步骤及预期结果 |
| `L2`     | 需覆盖全部最小必要集，测试用例应细化到可直接执行和验证的粒度 |
| `L3`     | 按阶段独立编写测试契约，当前阶段的测试范围仅聚焦本阶段实际交付的功能，避免提前覆盖后续阶段内容 |

三份交付契约并非相互独立，而是相互关联、相互约束的整体。编写和审核时应重点关注以下关联关系：

| 关联点              | 说明                                                         |
| ------------------- | ------------------------------------------------------------ |
| 产品契约 → 技术契约 | 技术契约中的接口设计和业务逻辑必须完整覆盖产品契约定义的业务规则，确保技术实现符合业务要求 |
| 技术契约 → 测试契约 | 测试契约中的每个接口及页面操作，都应在对应的技术契约中有明确的实现方案 |
| 测试契约 → 产品契约 | 测试用例的预期结果必须符合产品契约定义的业务规则及验收标准   |
| 版本一致性          | 同一需求、同一版本下的三份契约必须相互配套，避免混用不同版本的契约 |

应重点检查上述关联关系是否存在矛盾、遗漏或定义不一致的问题，确保三份契约在业务、技术和测试层面形成完整闭环。

| 关联点 | 说明 |
|--------|------|
| 项目上下文 → 产品契约 | 产品契约中的业务术语应与项目上下文的领域术语表保持一致 |
| 项目上下文 → 技术契约 | 技术契约的技术实现必须遵循项目上下文定义的架构原则、分层约束及命名规范 |
| 项目上下文 → 测试契约 | 测试契约的验证方式应符合项目上下文中的代码风格与基础约定 |
