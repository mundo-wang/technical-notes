这篇笔记明确契约驱动开发中的文档目录结构、各文档的创建规则与具体模板，使流程具备可直接落地的文档支撑。

项目文档应保持精简，避免无限膨胀。建议采用以下目录结构：

```scss
project/
├── AGENTS.md                      # AI项目开发规范与行为约束
│
├── docs/
│   ├── project/
│   │   ├── 项目概述.md            # 项目背景、核心概念、项目约束
│   │   ├── 架构设计.md            # 系统架构、模块职责、技术设计
│   │   └── 编码规范.md            # 开发约束、编码规则、工程规范
│   │
│   ├── requirements/
│   │   └── REQ-001-需求名称/
│   │       ├── 产品交付契约.md    # 业务需求与验收标准
│   │       ├── 技术交付契约.md    # 技术方案与约束
│   │       └── 测试交付契约.md    # 测试场景与验证要求
│   │
│   └── decisions/
│       └── ADR-001-决策名称.md    # 重要架构决策及原因
│
├── internal/                       # 业务代码
├── migrations/                     # 数据库迁移文件
└── ...
```

`REQ-001`是需求唯一标识。复杂需求拆分成多个版本时，可以在同一个需求目录下继续维护版本契约，也可以根据实际规模拆分子需求目录。

不同复杂度需求的文档要求存在差异。`AGENTS.md`与项目上下文在三种复杂度下均为读取已有文档或按需读取。产品交付契约在简单需求下为轻量需求说明，在普通与复杂需求下为必须。技术交付契约在简单需求下为可选，在普通与复杂需求下为必须。测试交付契约在简单需求下为验收标准简述，在普通与复杂需求下为必须。`ADR`在简单需求下不要求，在普通与复杂需求下按需创建。版本拆分在简单需求下不要求，普通需求下按需，复杂需求下必要时进行。

| 文档 | 简单需求 | 普通需求 | 复杂需求 |
| ---- | -------- | -------- | -------- |
| `AGENTS.md` | 使用已有文档 | 使用已有文档 | 使用已有文档 |
| 项目上下文 | 按需读取 | 按需读取 | 按需读取 |
| 产品交付契约 | 轻量需求说明 | 必须 | 必须 |
| 技术交付契约 | 可选 | 必须 | 必须 |
| 测试交付契约 | 验收标准简述 | 必须 | 必须 |
| `ADR` | 不要求 | 按需 | 按需 |
| 版本拆分 | 不要求 | 按需 | 必要时 |

项目上下文由`3`份核心文档组成，形成明确的职责划分。项目概述.md记录业务背景、核心概念与项目约束，在业务知识发生变化时更新。架构设计.md记录系统架构、模块职责与技术设计，在架构或技术设计发生变化时更新。编码规范.md记录开发约束、编码规则与工程规范，在开发规范发生变化时更新。需求开发时，`AI`先读取编码规范.md，再根据当前任务读取项目概述.md和架构设计.md中的相关内容。开发完成后，`AI`只检查这`3`份文档是否需要更新，不再维护额外的项目上下文文档。

项目概述.md用于记录项目整体背景与业务知识，回答「这个项目是做什么的」。其参考结构如下：

```markdown
# 项目概述

## 一、项目背景
项目的业务背景、建设目的及核心目标。

## 二、核心业务
主要业务领域、核心功能及业务流程概述。

## 三、业务术语
重要业务概念、专业术语及其含义。

## 四、项目约束
业务限制、特殊约定及其他无法从代码中直接获取的信息。

## 五、其他重要说明
需要AI了解但无法归入以上章节的内容。
```

架构设计.md将业务架构、技术架构、项目结构、数据库设计、公共模块等信息合并，回答「项目是如何组织和运行的」。需要注意的是，这里不是要求完整复制数据库表结构或代码目录，能够通过代码、配置、`ORM`模型自动获取的信息，尽量不重复维护。其参考结构如下：

```markdown
# 架构设计

## 一、整体架构
系统整体架构、核心组件及交互关系。

## 二、技术架构
主要技术栈、框架选型及技术方案。

## 三、业务架构
核心业务模块、模块职责及业务之间的关系。

## 四、项目结构
主要目录结构、目录职责及组织约定。

## 五、数据库设计
核心数据模型、重要表结构及表之间的关系。

## 六、公共模块
公共组件、基础设施模块及其职责、使用约定。

## 七、外部依赖
第三方服务、外部系统及交互方式。

## 八、关键技术决策
重要架构决策、设计原因及技术限制。
```

编码规范.md记录项目开发过程中必须遵循的规范，回答「代码应该如何编写」。其参考结构如下：

```markdown
# 编码规范

## 一、通用规范
命名规范、代码风格、目录组织及通用开发约定。

## 二、语言规范
语言特性使用约定、错误处理及代码组织方式。

## 三、框架规范
框架使用约定、中间件、依赖注入及模块设计规范。

## 四、数据库规范
数据库操作、事务处理、查询规范及数据访问约定。

## 五、接口规范
API设计、请求响应格式、错误码及接口兼容性要求。

## 六、日志与异常处理
日志规范、异常处理、错误传递及可观测性要求。

## 七、测试规范
测试组织、测试编写原则及测试覆盖要求。

## 八、安全规范
权限校验、输入验证、敏感信息处理及安全开发要求。

## 九、其他开发约定
项目特有的开发限制及补充规范。
```

交付契约分为产品交付契约、技术交付契约和测试交付契约三类。产品交付契约描述需求的业务目标与产品行为，纯技术需求不需要创建该文档。其参考模板如下：

```markdown
# 产品交付契约

## 一、需求背景
需求产生的原因及业务背景。

## 二、需求目标
本次需求需要解决的问题及预期结果。

## 三、功能范围
### 3.1 本次包含
明确本次需要实现的功能。

### 3.2 本次不包含
明确本次不涉及的功能，避免范围扩张。

## 四、业务规则
详细描述核心业务逻辑、判断条件及处理规则。

## 五、业务流程
描述正常流程、异常流程及状态流转。

## 六、边界条件
特殊场景、异常输入及边界情况。

## 七、验收标准
明确需求完成的判断标准。

## 八、待确认事项
尚未明确且需要开发者决策的问题。
```

技术交付契约描述需求的技术实现约束与设计方案，简单需求可以只保留「技术目标」「影响范围」「技术约束」及必要的验收标准。技术内容应区分三类：强制约束是必须遵守的架构、技术规范及业务限制；推荐方案是`AI`应优先采用但允许在合理情况下调整的内容；实现细节是不影响契约目标的具体编码方式，允许`AI`自主优化。其参考模板如下：

```markdown
# 技术交付契约

## 一、技术目标
本次技术改造的目的及预期效果。

## 二、影响范围
涉及的模块、接口、数据结构及基础设施。

## 三、技术方案
核心实现方案、模块职责及交互设计。

## 四、技术约束
### 4.1 强制约束
必须遵循的架构、技术规范及兼容性要求。

### 4.2 推荐方案
建议采用的方案及适用原因。

## 五、数据库变更
表结构、索引、字段变更及相关影响。

## 六、数据迁移
迁移策略、执行顺序、历史数据处理及回滚方案。

## 七、兼容性要求
接口兼容、数据兼容及新旧版本兼容要求。

## 八、非功能性要求
性能、安全、可靠性、可维护性及其他必要要求。

## 九、风险与注意事项
潜在技术风险、限制及需要关注的问题。

## 十、技术验收标准
明确技术实现的验收条件。
```

测试交付契约描述需求需要满足的验证目标，它描述的是需要验证什么，而不是要求所有测试必须在契约生成阶段立即执行。其参考模板如下：

```markdown
# 测试交付契约

## 一、测试目标
本次需求需要验证的核心行为及质量目标。

## 二、测试范围
涉及的功能、模块、接口及数据变更。

## 三、核心测试场景
### 3.1 正常场景
正常输入、正常流程及预期结果。

### 3.2 异常场景
异常输入、异常流程及错误处理。

### 3.3 边界场景
边界条件、特殊状态及极端情况。

## 四、数据一致性验证
数据库、缓存及跨模块数据一致性要求。

## 五、兼容性验证
接口、数据及已有功能兼容性要求。

## 六、数据库迁移验证
迁移前后数据正确性、完整性及恢复能力。

## 七、非功能性验证
必要的性能、安全及可靠性验证。

## 八、验收标准
明确测试通过的判断条件。

## 九、待执行验证
需要环境、依赖或其他前置条件的验证事项。
```

建议为每个需求维护文档状态生命周期。需求分析阶段创建并持续完善契约。契约审查阶段进行审查、修改与补充。开发阶段契约允许调整。开发完成阶段契约应与实际实现保持一致。进入测试阶段后契约冻结。测试验收阶段依据冻结契约进行验证。上线交付阶段契约保持冻结。后续需求变更时创建新的变更流程。进入测试阶段后，三份交付契约正式冻结。后续修改不能直接覆盖原有契约，应重新进入需求分析与契约确认流程。如果测试阶段发现问题，不应直接修改已冻结的原始契约，而是创建新的变更记录，关联原需求，并重新进入对应流程。

最后，不要将「文档模板完整」误解为「每份文档必须填满所有章节」。所有模板都应遵循以下规则：无关章节直接删除，不保留空章节；简单需求允许合并文档；仅记录当前需求涉及的内容；不确定的内容标记为待确认，不允许`AI`自行编造；契约中的验收标准必须明确、可判断；允许`AI`根据需求复杂度调整文档结构，但不得遗漏必要的约束与验收信息。
