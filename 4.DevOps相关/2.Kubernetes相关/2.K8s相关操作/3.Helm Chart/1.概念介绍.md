`Helm`是`Kubernetes`的包管理工具，可以类比`Linux`生态中的`apt`、`yum`，以及编程语言生态中的`npm`、`pip`。它的核心职责是将部署在`K8s`上的一组相关资源，如`Deployment`、`Service`、`ConfigMap`、`Ingress`等，打包成一个可复用、可配置、可版本化的部署单元，这个单元在`Helm`中被称为`Chart`。

在原生`K8s`管理方式下，部署一个中等复杂度的应用通常需要维护多份`YAML`文件。例如，一个`Web`服务可能需要`Deployment`管理副本、`Service`暴露端口、`ConfigMap`注入配置、`Secret`管理凭证、`Ingress`配置域名，以及`Namespace`和`RBAC`权限。这些文件存在大量重复或关联字段，例如`namespace`需要保持一致，镜像版本需要同步更新，不同环境的差异也往往需要复制文件并逐一修改。当应用和环境增多、版本迭代频繁时，单纯依赖`YAML`管理会越来越难以维护。

`Helm`正是为了解决这些问题而设计的。它可以将上述资源统一组织到一个`Chart`中，并通过模板引擎将可变部分抽象为配置参数。用户只需在安装或升级时提供`values`文件或命令行参数，`Helm`即可根据目标环境生成完整的`YAML`并部署到集群。同时，`Helm`会记录安装和升级的版本历史，并支持升级与回滚，让应用的发布和变更管理更加接近传统软件包管理。

`Helm`的体系围绕三个核心概念构建，理解它们是使用`Helm`的基础：

1. `Chart`：`Helm`的应用包，包含一组`K8s`资源模板和默认配置，是应用部署的静态定义。
2. `Release`：`Chart`在集群中的一次运行实例。同一个`Chart`可以安装多次，每次安装都会产生一个独立的`Release`。
3. `Repository`：`Chart`的远程或本地仓库，用于存储和分发`Chart`，类似`Docker Hub`之于容器镜像。

三者的关系可以简单概括为，从`Repository`获取`Chart`，将其安装到集群后生成一个`Release`。同一个`Chart`可以创建多个独立的`Release`，每个`Release`都拥有自己的版本历史和运行状态。

`Helm`作为客户端工具，只需安装在能够访问`K8s`集群的机器上即可，通常与`kubectl`部署在同一台管理节点上。

这里我们在`Master`节点下载`Helm`安装脚本并执行：

```bash
curl -fsSL -o get_helm.sh https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-4
chmod 700 get_helm.sh
./get_helm.sh
```

安装完成后，执行下面命令验证版本：

```bash
helm version
```

显示如下内容，表示已安装成功：

```json
version.BuildInfo{Version:"v4.3.0", GitCommit:"bec5b06ed841fe5269972d864d5177944fd5970f", GitTreeState:"clean", GoVersion:"go1.27.1", KubeClientVersion:"v1.37"}
```

`Helm v4.0.0`于`2025`年`11`月正式发布，这是`Helm`时隔六年的首次重大版本升级，同时也标志着`Helm`在云原生计算基金会的指导下迈入十周年。本文后续内容均基于`Helm v4`。

`Helm`的命令设计直观，大致可分为仓库管理、`Chart`管理、`Release`管理三类，以下是其常用命令：

| 命令                      | 作用                                 |
| ------------------------- | ------------------------------------ |
| `helm repo add`           | 添加`Chart`仓库                      |
| `helm repo list`          | 列出已添加的仓库                     |
| `helm repo update`        | 更新仓库索引，获取最新`Chart`列表    |
| `helm search repo`        | 在已添加的仓库中搜索`Chart`          |
| `helm search hub`         | 在`Artifact Hub`上搜索`Chart`（跨仓库） |
| `helm pull`               | 下载`Chart`到本地，不安装            |
| `helm show values`        | 查看`Chart`支持的配置项及默认值      |
| `helm show readme`        | 查看`Chart`的`README`文档          |
| `helm install`            | 安装`Chart`，在集群中创建`Release`（默认启用`SSA`） |
| `helm list`               | 列出集群中所有`Release`              |
| `helm status`             | 查看指定`Release`的状态和元信息      |
| `helm upgrade`            | 升级`Release`到新的`Chart`版本或配置（`SSA`默认`auto`） |
| `helm rollback`           | 将`Release`回滚到指定历史版本（`SSA`默认`auto`） |
| `helm uninstall`          | 卸载`Release`，删除其管理的所有`K8s`资源 |
| `helm history`            | 查看`Release`的版本历史              |
| `helm get values`         | 查看`Release`当前生效的配置值        |
| `helm get manifest`       | 查看`Release`实际渲染出的`K8s`资源清单 |
| `helm create`             | 在本地创建一个新的`Chart`脚手架      |
| `helm lint`               | 检查`Chart`的语法和最佳实践          |
| `helm package`            | 将`Chart`打包为`.tgz`文件以便分发（支持可复现构建） |

`Helm 4`采用`apiVersion: v2`的`Chart`规范。我们通过`helm create`命令创建一个`Chart`：

```bash
helm create mychart
```

该命令会生成名为`mychart`的目录，并在其中创建默认的`Chart`目录结构，如下所示：

```scss
mychart/
├── charts/
├── Chart.yaml
├── templates/
│   ├── deployment.yaml
│   ├── _helpers.tpl
│   ├── hpa.yaml
│   ├── httproute.yaml
│   ├── ingress.yaml
│   ├── NOTES.txt
│   ├── serviceaccount.yaml
│   ├── service.yaml
│   └── tests/
│       └── test-connection.yaml
└── values.yaml
```

其中，`Chart.yaml`回答「我是谁？」，`values.yaml`回答「我有哪些可配置参数？」，`templates/`回答「根据这些参数，最终生成什么`Kubernetes`资源？」，`charts/`则存放当前`Chart`所依赖的其他`Chart`。

`Helm`与原生`kubectl`操作管理的对比如下所示：

| 维度       | `kubectl`原生管理                         | `Helm`管理                                          |
| ---------- | ----------------------------------------- | --------------------------------------------------- |
| 资源组织   | 多份独立`YAML`文件，手工维护资源关联关系  | 打包为`Chart`，资源内聚且结构标准化                 |
| 配置复用   | 不同环境需复制多份文件并手动修改差异      | 通过`values.yaml`参数化，一套模板复用多个环境       |
| 版本管理   | 无内置版本历史，升级与回滚需要人工操作    | 自动记录`Release`修订历史，支持一键升级与回滚       |
| 依赖管理   | 不支持应用级依赖管理，依赖组件需单独部署  | 在`Chart.yaml`中声明依赖，自动下载并协调安装顺序    |
| 冲突处理   | 多个工具管理同一资源时容易产生字段冲突    | 默认启用`SSA`，通过服务器端字段管理减少冲突         |
| 回滚能力   | 需要手动保存历史`YAML`并重新执行`apply`   | 通过`helm rollback`一键回滚到指定历史版本           |
| 分发与共享 | 主要通过复制`YAML`文件或`Git`仓库进行传递 | 通过`Repository`发布和下载，支持`OCI`及`digest`校验 |
| 适用场景   | 单资源调试、学习、简单的一次性部署        | 复杂应用部署、多环境管理、持续交付流水线            |

在实际工作中，两者并非互斥。日常的资源查看、日志排查和临时调试仍主要通过`kubectl`完成，而应用的安装、升级、回滚以及多环境管理则交给`Helm`处理，这是较为常见的工作模式。
