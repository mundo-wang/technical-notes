`docker run`命令除了常用选项外，还提供了一系列资源限制参数，用于控制容器可使用的`CPU`、内存、`IO`等资源。在生产环境中，如果不对容器进行资源限制，单个容器可能因程序异常耗尽宿主机资源，从而影响其他容器，甚至导致宿主机本身受到影响。

这些限制参数的底层基于`Linux`的`CGroup`（控制组）机制实现。`CGroup`是`Linux`内核提供的资源管理能力，可以将进程划分为不同的组，并为每组进程设置相应的资源使用规则。`Docker`启动容器时，会在`CGroup`对应的子系统中为容器创建独立的控制组，并将`--memory`、`--cpus`等参数转换为对应的配置值，最终由内核负责强制执行。

`CPU`相关的限制参数主要有以下几种：

- `--cpus`：用于限制容器可使用的`CPU`核心数，支持小数。例如，`--cpus="1.5"`表示容器最多使用相当于`1.5`个`CPU`核心的计算能力。它本质上是`--cpu-quota`和`--cpu-period`的简化配置，默认周期通常为`100ms`。当设置为`1.5`个`CPU`时，表示每个周期内最多获得约`150ms`的`CPU`时间。因此，它并不是将容器绑定到`1.5`个物理核心，而是限制容器能够获得的总`CPU`时间。
- `--cpu-shares`：设置`CPU`相对权重，默认值为`1024`。当宿主机`CPU`资源紧张、多个容器同时争抢资源时，权重较高的容器可以分配到更多`CPU`时间。需要注意的是，权重仅在存在资源争抢时生效；当`CPU`资源充足时，容器仍可以使用全部可用核心。
- `--cpuset-cpus`：将容器限制在指定的`CPU`核心上运行。例如`--cpuset-cpus="0,2"`表示容器只能在`CPU 0`和`CPU 2`上运行，适用于对`CPU`缓存亲和性等方面有要求的场景。

限制容器使用`1.5`个`CPU`核心：

```sh
docker run -d --cpus="1.5" --name <container_name> <image_name>
```

给容器设置`CPU`相对权重为`512`：

```sh
docker run -d --cpu-shares=512 --name <container_name> <image_name>
```

将容器绑定到指定的`CPU`核心：

```sh
docker run -d --cpuset-cpus="0,2" --name <container_name> <image_name>
```

当容器的实际计算需求超过`--cpus`限制时，`CGroup`会对容器内进程进行`CPU throttling`，限制其在当前调度周期内能够获得的`CPU`时间。应用层面通常表现为响应变慢、处理延迟增加，但`CPU throttling`本身不会直接杀死进程。

可以通过`CGroup`的`cpu.stat`查看容器的`CPU`节流统计信息。其中，`nr_throttled`表示发生`CPU throttling`的周期数，`throttled_usec`表示因节流而受到限制的累计时间。具体查看方式取决于宿主机使用的是`CGroup v1`还是`CGroup v2`。如果`nr_throttled`和`throttled_usec`持续增长，说明容器正在频繁受到`CPU`配额限制。此时应结合应用实际的`CPU`使用率、请求延迟和业务负载进行综合判断，必要时适当提高`--cpus`限制或优化应用的`CPU`资源消耗。

内存相关的限制参数主要有以下几种：

- `--memory`：限制容器可使用的内存上限。例如，`--memory="512m"`表示容器的内存使用量上限为`512MB`。超过该限制时，容器可能触发`OOM`（`Out of Memory`），内核会根据`OOM`策略终止相关进程，容器也可能因此退出。
- `--memory-swap`：限制容器可使用的内存总量，即物理内存与`swap`之和。该值通常需要大于或等于`--memory`。如果设置为与`--memory`相同，则容器不能使用额外的`swap`空间；如果设置为`-1`，则表示不限制容器可使用的`swap`总量。

限制容器使用`512MB`物理内存，`768MB`总内存：

```sh
docker run -d --memory="512m" --memory-swap="768m" --name <container_name> <image_name>
```

当容器内存使用超过`--memory`限制时，`Linux`内核的`OOM Killer`可能会介入，根据`OOM`策略选择符合条件的进程终止，以释放内存资源。容器因`OOM Kill`导致主进程被`SIGKILL`终止时，退出码通常为`137`（`128 + 9`，其中`9`对应`SIGKILL`信号）。但`137`并不能单独证明容器发生了`OOM Kill`，因为其他原因导致进程收到`SIGKILL`时也可能返回该退出码。

可以通过以下命令查看容器的退出码：

```bash
docker inspect -f '{{.State.ExitCode}}' <container_name>
```

如果需要确认是否发生了`OOM Kill`，还应结合容器的`OOMKilled`状态以及宿主机或`CGroup`的内存事件进行判断。例如：

```bash
docker inspect -f '{{.State.OOMKilled}}' <container_name>
```

如果输出为`true`，则可以确认该容器发生了`OOM Kill`。

也可以通过系统日志查看`OOM`详情：

```sh
dmesg | grep -i "killed process"
```

`OOM`的应对策略主要包括：合理设置`--memory`并预留`20%~30%`的内存缓冲；如果业务允许，可以适当使用`swap`，但`swap`的性能远低于物理内存，不应将其作为常规内存资源依赖；同时从应用层面优化内存使用，降低不必要的内存占用。

对于关键业务容器，可以配合`--restart=on-failure`或`--restart=unless-stopped`实现异常退出后的自动恢复。

磁盘`IO`相关的限制参数主要有以下几种：

- `--blkio-weight`：设置磁盘`IO`权重，取值范围为`10`到`1000`，默认值为`500`。权重越高，在多个容器发生磁盘`IO`资源争抢时获得的带宽越多。与`--cpu-shares`类似，该权重仅在存在`IO`资源争抢时生效。
- `--device-read-bps`：限制容器对指定设备的读取速率。
- `--device-write-bps`：限制容器对指定设备的写入速率。

设置容器的`IO`权重为`300`：

```sh
docker run -d --blkio-weight=300 --name <container_name> <image_name>
```

限制容器对`/dev/sda`的读写速率不超过`10MB/s`：

```sh
docker run -d \
  --device-read-bps /dev/sda:10mb \
  --device-write-bps /dev/sda:10mb \
  --name <container_name>
  <image_name>
```

当容器的磁盘`IO`达到速率限制时，后续`IO`请求会受到限速，从而出现阻塞或延迟。应用层面可能表现为数据库查询变慢、日志写入卡顿、文件操作超时等。与内存`OOM`不同，磁盘`IO`限速不会导致进程被杀死，但会直接影响应用的响应性能和处理吞吐量。

查看容器的资源限制配置，命令如下：

```sh
docker inspect <container_name> | grep -A 20 "HostConfig"
```

也可以直接查看某项配置，命令如下：

```sh
docker inspect -f '{{.HostConfig.Memory}}' <container_name>
docker inspect -f '{{.HostConfig.CpuQuota}}' <container_name>
```

对于正在运行的容器，可以使用`docker update`动态调整部分资源限制，无需重启容器：

```sh
docker update --memory="1g" --cpus="2" <container_name>
```

`docker update`可以动态调整运行中容器的部分资源限制，包括`--cpus`、`--memory`、`--memory-swap`、`--cpu-shares`、`--cpuset-cpus`、`--pids-limit`等参数，无需重启容器即可生效。

生产环境中资源限制的配置建议如下：

| 资源类型 | 建议配置 | 注意事项 |
| -------- | -------- | -------- |
| `CPU` | 根据应用负载设置`--cpus`，不要过度限制核心计算型应用 | 关注`throttling`指标，频繁节流说明限制过严 |
| 内存 | 设置`--memory`，并预留`20%~30%`缓冲 | 不设置`--memory`等于无限制，风险极高 |
| 磁盘`IO` | 对日志密集型或数据库容器设置`--device-read-bps`/`--device-write-bps` | 权重仅在有争抢时生效，速率限制更直接 |
| 进程数 | 对不可信或复杂应用设置`--pids-limit` | 防止`fork`炸弹类攻击或意外进程泄漏 |

资源限制并非越低越好，过度限制可能导致应用性能下降，甚至频繁触发`OOM Kill`。因此，建议先通过监控了解应用的实际资源使用情况，再结合业务负载设置合理的资源限制值。
