但是，`/etc/resolv.conf`是由`NetworkManager`生成的，重启网络或系统后会被覆盖，所以我们要做长期配置。

首先确认该服务器的网络连接名称，执行如下命令：

```sh
nmcli connection show
```

命令执行输出如下所示：

<img src="image/image-20260227143705743.png" alt="image-20260227143705743" style="zoom:40%;" />

这表示当前使用的连接名是`enp0s1`。

下面做持久化配置，让`NetworkManager`不再自动获取`DNS`，而是固定使用`8.8.8.8`和`1.1.1.1`。我们按顺序执行以下命令：

```sh
nmcli connection modify enp0s1 ipv4.ignore-auto-dns yes
nmcli connection modify enp0s1 ipv4.dns "8.8.8.8 1.1.1.1"
nmcli connection down enp0s1 && nmcli connection up enp0s1
```

执行成功的结果如下所示：

<img src="image/image-20260429134333135.png" alt="image-20260429134333135" style="zoom:40%;" />

执行完成后，再执行一下下面的命令，验证持久化是否正确：

```sh
cat /etc/resolv.conf
nmcli device show enp0s1 | grep IP4.DNS
```

展示出如下结果，表示已配置成功：

<img src="image/image-20260227143930632.png" alt="image-20260227143930632" style="zoom:40%;" />

后续可以使用`reboot`命令重启机器，再执行上面的验证命令，看看是否为公共`DNS`。

如果想更改本机的`IP`地址，先查看当前网关和`IP`段，用于确认要设置的静态`IP`范围：

```sh
ip route show
```

查看到的结果如下所示：

```sh
default via 192.168.64.1 dev enp0s1 proto dhcp src 192.168.64.12 metric 100
192.168.64.0/24 dev enp0s1 proto kernel scope link src 192.168.64.12 metric 100
```

这表示网段为`192.168.64.0/24`，网关为`192.168.64.1`，当前动态分配的地址为`192.168.64.12`。

可在`192.168.64.2`到`192.168.64.254`之间选择一个目标地址，然后在终端执行以下命令：

```sh
nmcli connection modify enp0s1 ipv4.method manual \
  ipv4.addresses "192.168.64.2/24" \
  ipv4.gateway "192.168.64.1" \
  ipv4.dns "8.8.8.8 1.1.1.1"
nmcli connection down enp0s1 && nmcli connection up enp0s1
```

其中`ipv4.addresses`后面的`IP`地址需替换为实际想固定的地址。

若该命令在`SSH`连接中执行，执行后终端会卡住，原因是`IP`已发生变更，原有连接因地址失效而中断。此时切换到`UTM`的本地终端，执行`ip -4 a`命令确认`IP`是否已更新：

<img src="image/image-20260429142910598.png" alt="image-20260429142910598" style="zoom:40%;" />

随后在`SSH`客户端中修改连接信息，重新建立连接即可。

`UTM`是基于`QEMU/KVM`的虚拟化工具。`QEMU`虚拟机通常通过虚拟时钟机制获取时间，其时间同步依赖宿主机（`Mac`）及虚拟机内部的时钟管理机制。当`Mac`进入睡眠后再唤醒，或`UTM`虚拟机被手动暂停后恢复时，会因虚拟时钟未及时校准而出现时间偏移。

我们在`CentOS`虚拟机终端执行以下命令，安装并启用`chrony`：

```sh
yum install chrony -y
systemctl enable --now chronyd
```

`chronyd`默认配置为`makestep 1.0 3`，表示仅在启动后的前`3`次时钟更新中，当系统时间偏差超过`1`秒时，允许直接跳变校正。超过该次数后，`chronyd`通常通过逐步调整时钟频率来修正时间偏差，而不会立即跳变。对于`UTM`虚拟机，宿主机睡眠唤醒或虚拟机暂停恢复可能导致数小时级别的时间偏差，此时，仅依靠渐进式校正需要较长时间才能恢复准确时间。

执行以下命令，修改`chronyd`配置，允许在任意时刻进行时间步进校正，不再受启动后前`3`次时钟更新的限制：

```sh
sed -i 's/makestep 1.0 3/makestep 1.0 -1/' /etc/chrony.conf
systemctl restart chronyd
chronyc -a makestep
```

其中，`makestep 1.0 -1`表示不限制允许时间步进的更新次数，只要系统时间偏差超过`1.0`秒，就允许直接跳变校正。

默认的「`CentOS Pool`」时间源在国内网络环境下可能存在同步质量不佳的问题，建议更换为阿里云或腾讯云的`NTP`服务器。

使用以下命令，将三个时钟源配置追加到`/etc/chrony.conf`文件末尾：

```sh
sudo tee -a /etc/chrony.conf > /dev/null <<'EOF'
server ntp.aliyun.com iburst
server ntp1.aliyun.com iburst
server ntp.tencent.com iburst
EOF
```

重启服务使配置生效：

```sh
systemctl restart chronyd
```

执行以下命令查看时间同步状态：

```sh
chronyc tracking
```

重点关注输出中的`Leap status`字段，正常情况下应显示为`Normal`：

<img src="image/image-20261028102612519.png" alt="image-20261028102612519" style="zoom:40%;" />

再查看当前时间源列表：

```sh
chronyc sources -v
```

确保存在可用的`NTP`时间源，且同步状态正常：

<img src="image/image-20261028103109535.png" alt="image-20261028103109535" style="zoom:40%;" />

在`chronyc sources -v`的输出中，`^`表示时钟源的类型为`NTP Server`，后面的符号表示该时钟源的状态：

| 标记 | 含义                     | 说明                                                 |
| ---- | ------------------------ | ---------------------------------------------------- |
| `^*` | 当前选中的时钟源         | `chronyd`当前优先使用该时钟源进行系统时间同步。      |
| `^+` | 可参与联合计算的时钟源   | 该时钟源的测量结果被纳入时间校正计算。               |
| `^-` | 未参与联合计算的时钟源   | 该时钟源可用，但当前未被选入联合计算集合。           |
| `^?` | 不可用或状态未知的时钟源 | 可能尚未收到有效响应、无法访问，或有效测量数据不足。 |
| `^x` | 被判定为异常的时钟源     | 该时钟源的时间与其他时钟源存在明显冲突，可能不可靠。 |
| `^~` | 波动较大的时钟源         | 测量结果的变化幅度过大，稳定性不足。                 |

完成以上配置后，即使`Mac`进入睡眠状态，或`UTM`中的虚拟机暂停后恢复，虚拟机也能在`chronyd`的运行周期内自动校正系统时间。
