`Prometheus`通过`scrape_configs`配置被监控的目标地址。在传统的静态环境中，运维人员可以直接在配置文件中填写固定的`IP`和端口。但在云原生和容器化环境中，服务的实例地址是动态变化的，`Pod`可能随时被创建或销毁，静态配置显然无法满足需求。因此，`Prometheus`提供了强大的服务发现（`Service Discovery`）机制，使其能够自动感知和跟踪目标的变化。

### 1. 静态配置

静态配置是最简单直接的方式，通过`static_configs`在配置文件中显式列出所有目标的地址和标签。

```yaml
scrape_configs:
  - job_name: 'node_exporter'
    static_configs:
      - targets: ['192.168.1.10:9100', '192.168.1.11:9100']
        labels:
          env: 'production'
```

这种方式适合监控地址固定的节点，例如物理机或虚拟机上部署的`Node Exporter`。但在微服务和`Kubernetes`环境下，静态配置的维护成本极高，几乎无法持续使用。

### 2. 动态服务发现

`Prometheus`内置了多种动态服务发现机制，可以与主流的编排平台和注册中心集成，自动获取目标列表。

#### 2.1 `Kubernetes SD`

`Kubernetes SD`是云原生场景下最常用的服务发现方式。`Prometheus`可以直接与`Kubernetes API Server`通信，自动发现集群内的多种资源对象，包括：

- `Pod`：发现所有`Pod`的`IP`地址，常用于 sidecar 模式采集业务指标。
- `Service`：发现`Service`的虚拟`IP`和端口。
- `Endpoints`：发现`Service`后端真实的`Pod`端点，是监控业务服务最常用的方式。
- `Node`：发现集群中所有工作节点的地址，用于部署`Node Exporter`。
- `Ingress`：发现`Ingress`资源的地址，配合`Blackbox Exporter`监控入口可用性。

例如，监控`default`命名空间下所有`Pod`的配置如下：

```yaml
scrape_configs:
  - job_name: 'kubernetes-pods'
    kubernetes_sd_configs:
      - role: pod
        namespaces:
          names:
            - default
```

#### 2.2 `Consul SD`

如果服务注册在`Consul`中，`Prometheus`可以通过`Consul SD`自动发现注册的服务实例。配置时需要指定`Consul`的地址和数据中心：

```yaml
scrape_configs:
  - job_name: 'consul-services'
    consul_sd_configs:
      - server: 'localhost:8500'
        datacenter: 'dc1'
        services: ['my-service']
```

`Prometheus`会定期从`Consul`拉取服务实例列表，并自动将新实例加入监控，将下线的实例移除。

#### 2.3 `DNS SD`

`DNS SD`通过`DNS SRV`记录来发现服务。适用于一些基于`DNS`做服务发现的场景，例如`Etcd`集群或某些遗留系统：

```yaml
scrape_configs:
  - job_name: 'dns-srv-discovery'
    dns_sd_configs:
      - names: ['_http._tcp.my-service.example.com']
        type: 'SRV'
```

#### 2.4 云厂商`SD`

`Prometheus`还支持直接与主流云平台的`API`对接，自动发现云上的资源实例，包括：

- `EC2 SD`：自动发现`AWS EC2`实例。
- `GCE SD`：自动发现`Google Cloud Engine`实例。
- `Azure SD`：自动发现`Azure`虚拟机。

这些`SD`机制通过云平台的`API`密钥获取实例列表，适合混合云或多云环境下的统一监控。

#### 2.5 `File SD`

`File SD`是一种轻量级的动态发现方式，`Prometheus`会监视指定的`JSON`或`YAML`文件，当文件内容发生变化时自动加载新的目标列表，无需重启`Prometheus Server`。

```yaml
scrape_configs:
  - job_name: 'file-sd'
    file_sd_configs:
      - files: ['/etc/prometheus/targets/*.json']
        refresh_interval: 5m
```

这种方式非常适合与`CMDB`或自定义的自动化平台对接，由外部系统生成目标文件，`Prometheus`被动感知变化。

### 3. `Relabeling`（重新标记）

服务发现返回的目标通常携带大量由平台自动生成的元数据标签（以`__meta_`为前缀），这些标签往往不能直接用于监控目的。`Prometheus`提供了`Relabeling`机制，允许在抓取前后对标签进行过滤、修改和映射。

`Relabeling`有两个配置位置：

- `relabel_configs`：作用于抓取之前，用于过滤目标或修改目标级别的标签。
- `metric_relabel_configs`：作用于抓取之后，用于过滤指标或修改指标级别的标签。

`Relabeling`支持的动作（`action`）包括：

| 动作 | 作用 |
| ---- | ---- |
| `keep` | 如果源标签匹配正则表达式，则保留该目标；否则丢弃。 |
| `drop` | 如果源标签匹配正则表达式，则丢弃该目标；否则保留。 |
| `replace` | 将源标签的值按正则表达式匹配并替换为目标标签的值。 |
| `labelmap` | 将匹配正则表达式的所有标签名进行批量映射。 |
| `labeldrop` | 删除匹配正则表达式的标签。 |
| `labelkeep` | 仅保留匹配正则表达式的标签，其余全部删除。 |

下面是一个典型的`Kubernetes`场景下的`relabel_configs`示例，只抓取带有特定注解的`Pod`：

```yaml
scrape_configs:
  - job_name: 'kubernetes-pods'
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: true
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_path]
        action: replace
        target_label: __metrics_path__
        regex: (.+)
      - source_labels: [__address__, __meta_kubernetes_pod_annotation_prometheus_io_port]
        action: replace
        regex: ([^:]+)(?::\d+)?;(\d+)
        replacement: $1:$2
        target_label: __address__
```

上述配置的执行逻辑如下：

1. 第一条规则检查`Pod`是否带有`prometheus.io/scrape: "true"`注解，如果没有则直接丢弃该`Pod`。
2. 第二条规则将`prometheus.io/path`注解的值映射为指标抓取路径，默认是`/metrics`。
3. 第三条规则将`prometheus.io/port`注解的值与`Pod IP`组合，生成最终的抓取地址。

`Relabeling`是`Prometheus`配置中最灵活但也最容易出错的部分。配置不当可能导致目标被意外丢弃，或者标签混乱影响后续查询。建议在修改`Relabeling`规则后，使用`Prometheus`的`Targets`页面查看每个目标的最终标签和状态，确保规则按预期生效。
