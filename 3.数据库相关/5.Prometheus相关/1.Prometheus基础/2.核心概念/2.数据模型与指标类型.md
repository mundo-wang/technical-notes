`Prometheus`采用多维数据模型来组织指标数据，这一设计是它区别于传统监控系统的核心特征之一。理解数据模型和指标类型，是后续编写`PromQL`查询和合理设计监控指标的前提。

### 1. 时间序列（`Time Series`）

在`Prometheus`中，一条时间序列由两部分唯一确定：指标名称（`Metric Name`）和一组标签（`Label`）。指标名称描述被测量的是什么，标签则用于区分同一指标在不同维度上的表现。

例如，下面是一条典型的时间序列：

```
http_requests_total{method="GET", status="200", path="/api/users"}
```

其中`http_requests_total`是指标名称，表示`HTTP`请求的总数；花括号内的`method="GET"`、`status="200"`、`path="/api/users"`是三个标签，分别代表请求方法、响应状态码和请求路径。同一指标名称配合不同的标签组合，可以产生大量不同的时间序列。

`Prometheus`在存储时，会将每个时间序列按时间顺序存储为一组样本（`Sample`），每个样本包含两个字段：一个浮点数值（`Value`）和一个精确到毫秒的时间戳（`Timestamp`）。

### 2. 四种核心指标类型

`Prometheus`客户端库（如`Go`的`client_golang`）定义了四种核心指标类型，分别适用于不同的计量场景。

`TYPE`用于声明指标类型。示例中的`gauge`和`counter`分别表示两种不同的指标类型：

- `gauge`：仪表盘类型，用于表示可以增加或减少的数值，例如当前温度、内存使用量、当前并发数、任务执行耗时等。本例中的`backup_duration_seconds 125.5`表示备份任务耗时为`125.5`秒。
- `counter`：计数器类型，用于表示从启动或重置以来单调递增的累计值，通常只会增加，特殊情况下可能因进程重启而重置。本例中的`backup_records_total 10240`表示累计备份记录数为`10240`。

除了这两种常用类型，`Prometheus`还有`histogram`（直方图），用于统计观测值在不同区间内的分布，常用于分析请求耗时；以及`summary`（摘要），用于统计观测次数、总和及指定分位数，常用于分析请求延迟的分位数表现。

#### 2.1 `Counter`（计数器）

`Counter`表示一个单调递增的计数值，除非进程重启，否则只增不减。它适用于统计累计发生次数的场景，例如请求总数、错误总数、任务完成次数等。

在`PromQL`中，直接使用`Counter`的原始值意义不大，通常需要配合`rate()`或`increase()`函数计算一段时间内的增长速率。例如，计算过去`5`分钟内每秒的平均请求数：

```promql
rate(http_requests_total[5m])
```

#### 2.2 `Gauge`（仪表盘）

`Gauge`表示一个可以任意上下浮动的当前值，适用于描述某个时刻的状态量。常见的`Gauge`指标包括内存使用量、`CPU`利用率、温度、连接池空闲数、队列当前长度等。

由于`Gauge`可以随时变化，在查询时通常直接取瞬时数值或计算平均值、最大值、最小值，不需要像`Counter`那样计算变化率。

#### 2.3 `Histogram`（直方图）

`Histogram`用于对观测值进行采样，并将其分到预设的桶（`Bucket`）中。客户端在定义`Histogram`时需要预先指定一组桶边界，例如`0.005`、`0.01`、`0.025`、`0.05`、`0.1`、`0.25`、`0.5`、`1`、`2.5`、`5`、`10`，单位通常是秒。

当一个`Histogram`指标被创建后，`Prometheus`会自动为其生成三条时间序列：

- `<basename>_bucket{le="<上限>"}`：统计落入该桶及以下的样本数量。
- `<basename>_sum`：所有观测值的总和。
- `<basename>_count`：观测值的总数量。

`Histogram`的典型应用场景是记录请求延迟分布或响应体大小分布。在服务端，可以通过`histogram_quantile()`函数计算任意分位值，例如计算`P95`延迟：

```promql
histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket[5m])) by (le))
```

上述查询先通过`rate()`计算每个`bucket`的每秒增长量，再用`sum by (le)`按`le`标签聚合所有实例的数据，最后由`histogram_quantile()`计算出全局的`P95`延迟。如果省略`sum by (le)`步骤，在多实例环境下`histogram_quantile`会分别对每个实例单独计算，无法得到正确的全局分位值。

`Histogram`的优势在于桶数据可以在多个实例之间进行聚合，适合大规模集群的汇总分析。

#### 2.4 `Summary`（摘要）

`Summary`同样用于记录观测值的分布，但与`Histogram`不同的是，它在客户端直接计算并暴露分位值（如`0.5`、`0.95`、`0.99`）。`Summary`内部使用滑动时间窗口算法，只保留最近一段时间的数据。

`Summary`的优点是客户端已经计算好了分位值，查询时无需服务端再做复杂运算。但它的缺点也很明显：由于分位值是在单个客户端实例上计算的，无法跨实例进行聚合。例如，两个实例各自的`P99`延迟不能直接平均得到整体的`P99`。

| 场景 | 推荐类型 | 原因 |
| ---- | -------- | ---- |
| 需要跨实例聚合分位值 | `Histogram` | 服务端可聚合`bucket`数据 |
| 追求精确分位值且数据无需聚合 | `Summary` | 客户端计算更精确 |
| 需要灵活调整分位边界 | `Histogram` | 可在服务端重新计算任意分位值 |

### 3. 高基数问题（`Cardinality`）

时间序列的数量等于指标名称与所有标签值组合数的乘积。如果某个标签的取值范围过大（例如将`user_id`、`request_id`、`ip`地址作为标签），时间序列的数量会呈爆炸式增长，这种现象称为高基数问题。

高基数会直接导致`Prometheus`内存占用激增、查询响应变慢，严重时甚至引发`OOM`（内存溢出）。

生产环境中的最佳实践包括：

- 标签值应尽量控制在有限的可枚举集合内，例如状态码、环境名称、服务版本等。
- 避免将用户`ID`、订单`ID`、会话`ID`等唯一标识作为标签，这些数据更适合写入日志系统或追踪系统。
- 定期审视现有指标的标签设计，清理冗余或高基数标签。

### 4. `PromQL`查询基础

`PromQL`（`Prometheus Query Language`）是`Prometheus`内置的查询语言，用于在时序数据中检索和聚合信息。本节只做最基础的铺垫，详细的语法和函数会在后续专题中深入讲解。

`PromQL`的查询结果分为两种向量类型：

- 瞬时向量（`Instant Vector`）：返回查询时刻的最新样本值，例如`http_requests_total`。
- 范围向量（`Range Vector`）：返回一段时间内的所有样本，需要在指标名后用方括号指定时间范围，例如`http_requests_total[5m]`。

常用的几个函数如下：

- `rate(v range-vector)`：计算范围向量中每秒的平均增长率，专用于`Counter`类型。
- `irate(v range-vector)`：计算范围向量中最后两个样本之间的瞬时增长率，对突发变化更敏感。
- `increase(v range-vector)`：计算范围向量中整个时间段内的总增长量。
- `histogram_quantile(φ float, b instant-vector)`：根据`Histogram`的桶数据计算分位值，`φ`的取值范围为`0`到`1`。

这些函数在实际编写告警规则和`Grafana`面板时会频繁用到，理解它们的行为对于高效使用`Prometheus`至关重要。
