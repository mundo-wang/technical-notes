本文将介绍`Prometheus`的整体架构设计与核心组件，帮助读者从宏观层面理解系统的数据流向，以及各模块的职责分工。

`Prometheus`是一款开源的系统监控与告警工具包，最初由`SoundCloud`开发，随后成为`CNCF`的毕业项目。它采用基于多维数据模型的时序数据存储方式，并提供灵活的`PromQL`查询语言，广泛应用于云原生环境下的监控场景。

`Prometheus`的整体架构围绕「主动拉取（`Pull`）」这一核心模式展开：由`Prometheus Server`主动向被监控目标发起`HTTP`请求，拉取指标数据，并将其存储到本地时序数据库中。整体数据流如下图所示：

`Prometheus Server`是整个监控体系的核心，负责指标的抓取、存储、查询和告警评估。它由以下几个内部模块组成：

- `Retrieval`（抓取器）：按照配置定时向目标发起`HTTP`请求，采集监控指标。
- `TSDB`（时序数据库）：负责存储采集到的时间序列数据，并支持高效的查询。
- `HTTP Server`：对外提供`Web UI`、`HTTP API`和指标查询接口。
- `Rule Manager`（规则管理器）：周期性评估告警规则和记录规则，触发告警或生成预计算指标。

`Retrieval`模块根据配置文件中的`scrape_configs`配置，按照指定的抓取间隔，定期向目标服务的`/metrics`端点发送`HTTP GET`请求，获取文本格式的监控指标数据。其核心配置结构如下：

```yaml
scrape_configs:
  - job_name: 'prometheus'
    static_configs:
      - targets: ['localhost:9090']
    scrape_interval: 15s
```

其中，`job_name`用于对同一类监控目标进行逻辑分组，`targets`列表用于指定具体的监控目标地址，`scrape_interval`则用于设置指标数据的抓取间隔。

`Prometheus`内置了自研的时序数据库`TSDB`，所有采集到的样本数据均存储在本地磁盘，无需依赖外部存储系统。

`TSDB`的核心设计特点包括：

- 按时间分片：数据以块（`chunk`）为单位组织，每个块覆盖固定的时间范围，过期数据可通过删除或压缩进行管理。
- 内存中的`Head`块：最新写入的数据首先保存在内存中，满足一定条件后再持久化到磁盘。
- 预写日志（`WAL`）：数据写入内存的同时记录到`WAL`文件，确保进程异常退出后能够通过日志回放恢复数据。
- 索引文件（`Index`）：建立指标名称和标签到数据位置的索引，加速时间序列的检索与查询。

`TSDB` 的数据默认存储在启动参数 `--storage.tsdb.path` 指定的目录下，典型结构如下：

```
/opt/prometheus/data/
├── chunks/
│   └── 000001
├── index
├── meta.json
├── tombstones
└── wal/
    ├── 00000000
    └── checkpoint.00000001/
```

各文件的含义如下：

| 文件/目录 | 说明 |
|-----------|------|
| `chunks/` | 存储压缩后的时序数据块，是磁盘上的主要数据文件 |
| `index` | 倒排索引，用于根据标签快速定位样本位置 |
| `meta.json` | 当前数据库块的元数据信息 |
| `tombstones` | 标记已删除的时间范围，延迟清理机制 |
| `wal/` | 预写日志目录，保证数据写入的持久性 |
| `wal/checkpoint.*` | `WAL` 的压缩检查点，用于加速重启恢复 |



`Prometheus` 内置 `HTTP Server`，默认监听 `9090` 端口，提供以下核心功能：

- **Web UI**：可视化查询界面，支持输入 `PromQL` 表达式并展示结果。
- **HTTP API**：提供 `/api/v1/query`、`/api/v1/query_range` 等端点，供外部系统（如 `Grafana`）调用。
- **管理端点**：包括 `/-/reload`（热加载配置）、`/-/healthy`（健康检查）、`/-/ready`（就绪检查）等。



`Rule Manager` 负责周期性评估两类规则：

- **Recording Rules（记录规则）**：预先计算复杂的 `PromQL` 表达式，将结果存储为新的时间序列，加速后续查询。
- **Alerting Rules（告警规则）**：根据条件判断是否触发告警，满足条件时向 `Alertmanager` 发送告警通知。

规则文件的典型配置如下：

```yaml
groups:
  - name: example
    rules:
      - record: job:http_inprogress_requests:sum
        expr: sum(http_inprogress_requests) by (job)

      - alert: HighRequestLatency
        expr: job:http_inprogress_requests:sum > 100
        for: 5m
        labels:
          severity: page
        annotations:
          summary: "High request latency on {{ $labels.instance }}"
```

## 周边生态组件

除了 `Prometheus Server` 本身，完整的监控体系还需要以下周边组件配合工作。

### Exporter

`Exporter` 是部署在被监控目标附近的中介程序，负责将目标系统的内部状态（如操作系统内核指标、数据库性能数据、消息队列状态等）转换为 `Prometheus` 能够解析的文本格式，并通过 `HTTP` 暴露 `/metrics` 端点。

`Prometheus` 社区维护了大量官方和第三方的 `Exporter`，常见的有：

| Exporter 名称 | 监控对象 | 默认端口 |
|--------------|----------|----------|
| `Node Exporter` | `Linux/Unix` 系统级指标（`CPU`、内存、磁盘、网络） | `9100` |
| `Blackbox Exporter` | 网络端点探测（`HTTP`、`TCP`、`ICMP`、`DNS`） | `9115` |
| `MySQL Exporter` | `MySQL` 数据库性能与状态指标 | `9104` |
| `Redis Exporter` | `Redis` 实例性能指标 | `9121` |
| `Kafka Exporter` | `Kafka` 集群 `Broker`、`Topic`、`Consumer Group` 指标 | `9308` |
| `Nginx Exporter` | `Nginx` 连接数、请求处理指标 | `9113` |

应用程序也可以直接集成 `Prometheus Client Libraries`，在代码中自定义并暴露业务指标，无需额外的 `Exporter`。

### Pushgateway

`Pushgateway` 是 `Prometheus` 生态中唯一的「推送」入口，用于解决短期任务或批处理作业无法被长期拉取的问题。

典型场景包括：

- 定时 `CronJob` 任务执行完成后立即退出，生命周期过短，无法被 `Prometheus` 周期性拉取。
- 运行在防火墙后的服务，`Prometheus Server` 无法主动访问其指标端点。

这些任务在执行结束后，可以将指标通过 `HTTP POST` 推送到 `Pushgateway`，由 `Pushgateway` 暂存并暴露，供 `Prometheus` 后续拉取。

需要注意的是，`Pushgateway` 仅适用于临时任务指标的汇聚，不适合作为常规服务的监控方案。过度使用 `Pushgateway` 会导致单点故障和指标管理混乱。

### Alertmanager

`Alertmanager` 负责接收 `Prometheus Server` 发送的告警通知，并进行以下处理：

- **分组（Grouping）**：将同类或同一批次的告警合并为一条通知，避免告警风暴。
- **抑制（Inhibition）**：当高优先级告警触发时，自动抑制低优先级的相关告警。
- **静默（Silencing）**：在维护窗口期间手动静默特定告警。
- **路由（Routing）**：根据标签匹配规则，将告警分发到不同的接收渠道（如邮件、`PagerDuty`、`Slack`、`Webhook` 等）。

`Prometheus` 与 `Alertmanager` 之间通过 `HTTP` 通信，`Prometheus` 将触发的告警以 `JSON` 格式推送到 `Alertmanager` 的 `/api/v1/alerts` 端点。

### Client Libraries

`Prometheus` 为多种编程语言提供了官方客户端库，方便开发者在应用程序代码中直接埋点、定义并暴露自定义指标。主流语言的支持情况如下：

| 语言 | 官方库 | 说明 |
|------|--------|------|
| `Go` | `github.com/prometheus/client_golang` | 功能最完善，生态最成熟 |
| `Java/Scala` | `io.prometheus:simpleclient` | 支持 `Spring Boot` 等主流框架 |
| `Python` | `prometheus-client` | 支持同步和异步暴露指标 |
| `Ruby` | `prometheus-client` | 轻量级实现 |
| `Node.js` | `prom-client` | 社区维护，功能丰富 |

客户端库的核心能力包括：定义 `Counter`、`Gauge`、`Histogram`、`Summary` 四种指标类型，自动组装 `HTTP /metrics` 端点，以及暴露符合 `Prometheus` 文本格式规范的指标数据。

## Pull 模式的设计哲学

`Prometheus` 采用 `Pull` 模式作为核心数据采集机制，这与传统监控系统中常见的 `Push` 模式形成鲜明对比。理解这一设计选择，有助于更合理地规划监控架构。

### Pull 模式的优势

- **易于控制**：`Prometheus Server` 自主决定何时拉取、拉取谁、拉取频率是多少，整个采集逻辑集中可控。
- **天然支持服务发现**：配合 `DNS`、`Consul`、`Kubernetes` 等服务发现机制，目标列表可以动态更新，无需被监控端感知。
- **利于故障定位**：如果某个目标抓取失败（`up` 指标为 `0`），可以立即判断是目标服务异常还是网络问题。
- **便于本地调试**：开发者可以直接在浏览器中访问目标服务的 `/metrics` 端点，查看暴露的指标数据。

### Pull 模式的局限与应对

- **短生命周期任务**：对于执行后即退出的批处理任务，`Prometheus` 来不及拉取其指标。应对此问题的标准方案是使用 `Pushgateway`。
- **防火墙与网络隔离**：当被监控端位于 `NAT` 或防火墙之后，`Prometheus` 无法主动访问其端点。此时同样可借助 `Pushgateway` 进行中转。
- **拉取频率限制**：过高的拉取频率会增加目标端和网络的开销。通常建议将 `scrape_interval` 设置在 `15s` 至 `60s` 之间，根据指标灵敏度需求权衡。

### 与 Push 模式的对比

| 维度 | Pull 模式 | Push 模式 |
|------|-----------|-----------|
| 数据流向 | 监控中心主动拉取 | 被监控端主动推送 |
| 目标管理 | 服务端集中配置，支持服务发现 | 被监控端需预先知道推送地址 |
| 网络要求 | 服务端需能访问目标端 | 目标端需能访问服务端 |
| 短任务支持 | 需借助 `Pushgateway` | 天然支持 |
| 故障诊断 | 通过 `up` 指标直观判断 | 需依赖心跳或超时机制间接判断 |
| 典型代表 | `Prometheus` | `Zabbix Agent`、`InfluxDB` |

`Prometheus` 的架构设计并未完全排斥 `Push` 模式，而是通过 `Pushgateway` 在特定场景下进行补充，从而在保持 `Pull` 模式核心优势的同时，覆盖更广泛的监控需求。
